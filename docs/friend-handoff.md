## 2. 공통 틀 — 새 방법을 붙이는 법

### 파일

```
app/
  core/app.js          공통: 설정·시작 화면, 위쪽 막대, 타이머, act(), kit(), 방법 고르기·기억
  core/parts.js        공통 부품(SokParts): 화면 조각
  core/ui.js           el(), 판정 문구(엘렌코스), helpFor()(도움말 계산, 모든 방법)
  methods/elenchus.js        엘렌코스 흐름(그대로)
  methods/elenchus-views.js  엘렌코스 화면 + 등록
  methods/friend.js          모르는 친구 흐름
  methods/friend-views.js    모르는 친구 화면 + 등록
  index.html           스크립트 순서: 데이터 → ui → parts → 방법 흐름 → 방법 화면 → app
```

### 등록

`methods/<이름>-views.js` 끝에서 등록합니다.

```js
(root.SokMethods = root.SokMethods || []).push({
  id, name,            // 시작 화면 선택지
  startHint,           // 시작 화면 아래 안내 한 줄
  createSession,       // ({ topic, textbookId, lessonId, llm, sourceText }) => 세션
  views: { input(kit), talk(kit), result(kit) },  // 각각 DOM 요소를 돌려줌
});
```

`index.html`(과 `tests/views.html`)에 두 스크립트를 넣고 `?v=숫자`를 붙입니다. 그러면 시작 화면에 저절로 나타납니다.

### 세션이 지켜야 할 약속

- `getState().phase`: `"input" | "waiting" | "asking" | "error" | "done"`
  - `input`이면 input 화면, `done`이면 result 화면, 나머지는 talk 화면입니다(`app.js`의 `viewFor`).
- `cancel()`: [다음 학생]·[처음으로]에서 부릅니다. 늦게 온 응답을 버려야 합니다(세대 번호).
- `retry()`: 오류 화면의 [다시 시도]에서 부릅니다.
- 나머지 동작(`submitExplanation`, `submitAnswer`, `finishNow` 등)은 방법이 정하고, 자기 화면에서만 부릅니다.

### kit (화면에 건네는 도구)

| 이름 | 하는 일 |
|---|---|
| `session`, `scope` | 지금 세션, 고른 범위(`topic`, `textbookId`, `choice.lessonId`, `lessonTitle`, `contextTitle`, `textbookName`, `lessonLabel`) |
| `act(promise)` | 세션 동작을 기다리며 화면을 다시 그림. 화면에서 세션을 부를 때 꼭 이것으로 감쌉니다 |
| `show(view)` | 화면 바꾸기 |
| `toast(msg)`, `onEnter(fn)`, `copy(text)` | 짧은 알림, Enter 보내기(Shift+Enter 줄바꿈·한글 조합 무시), 복사 |
| `elapsedText()`, `today()` | 걸린 시간, 날짜 글 |
| `nextStudent()`, `openSettings()` | [다음 학생], [설정] |

### 공통 부품 (`SokParts`)

| 부품 | 쓰는 곳 |
|---|---|
| `goal(title)` | 맨 위 학습문제 |
| `dots(done, max)` | 질문 진행 점 |
| `thinkingCard(who, dots)` | "생각하는 중" 카드 |
| `questionCard(who, dots, question, extra)` | 질문 카드(`extra`가 있으면 질문 위에 반응 한 줄) |
| `answerArea(kit, { send, finish })` | 답 입력칸 + [보내기] [바로 정리하기] |
| `errorArea(kit)` | 오류 문구 + [다시 시도] |
| `helperBox(help, title)`, `helpLines(help)` | 선생님 도움말 상자, 그 안의 줄(있는 칸만). 첫 칸 이름은 `help.itemLabel`, 없으면 "살펴볼 생각"(모르는 친구는 "살펴볼 질문") |
| `recordBox(lines)` | 접히는 문답 기록(인쇄할 때 펼침) |
| `resultActions(kit, text)` | [복사] [인쇄] [다음 학생] |

선생님 도움말은 `SokUI.helpFor(topic, textbookId, { item, misconception, lessonId })`로 계산합니다. 오개념 id를 주면 그 오개념의 바른 생각과 이어서 물어볼 것이 나옵니다.

### 스타일

`core/style.css` 하나입니다. 방법별 클래스는 이름이 겹치지 않게 붙입니다(예: `.explain-box`, `.marks`, `.mark.explained`). 빨간색·X·점수는 쓰지 않습니다. 모르는 친구의 표시 색은 초록(잘 설명)·청록(바로잡음)·호박색(함께 더)입니다.

## 3. 화면 비교 틀 (`tests/views.html`)

리팩터나 공통 부품을 고칠 때, 다른 방법의 화면이 바뀌지 않았는지 키 없이 확인합니다.

- `?run=elenchus&compare=1`: 엘렌코스 10장면을 `tests/fixtures/elenchus-views-baseline.js`(리팩터 전 HTML)와 비교합니다. **"같음 10/10"이어야 합니다.** 기준 파일은 고치지 않습니다.

- `&stop=장면이름`: 그 장면에서 멈춥니다(스크린샷용).

- 공통 화면이 일부러 바뀌면 `ADJUST`에 그 차이만 적습니다. 예: 시작 화면에 "모르는 친구" 선택지가 생긴 것.

2. 엘렌코스 비교가 10/10인지 확인합니다.

## 4. 모르는 친구가 하는 일

### 화면 흐름
1. **입력**: 학습문제 → "친구에게 오늘 배운 것을 설명해 볼까요?" 한 칸.
2. **문답**: 학생 설명을 작게 보여 주고, 친구의 질문이 최대 3개 이어집니다. 질문 위에 친구의 짧은 반응이 붙습니다.
3. **결과**: 질문마다 표시, 친구의 한마디, 다음 시간 확인할 것, 선생님 도움말, 문답 기록, [복사][인쇄][다음 학생].

### 질문 종류와 차례 (코드가 정함, `kindsFor`)

| 질문 | 고를 수 있는 종류 |
|---|---|
| 1번 | 뜻·까닭(`meaning`), 더 말해(`more`), 다시 말해(`retry`) |
| 2번 | 잘못 알아듣기(`mixup`). 쓸 오개념이 남아 있지 않으면 `meaning` |
| 3번 | `meaning` 또는 `mixup` |

- 응답 형식의 `kind` enum을 이 목록으로 좁혀 보냅니다.
- `mixup`이면 오개념 id가 범위 안에 있어야 하고, 앞에서 쓴 것이면 안 됩니다.

### 표시 (앞 질문의 종류와 짝)
- `mixup` 뒤: `corrected`(친구를 바로잡았어요) 또는 `together`(함께 더 알아봐요)
- 그 밖: `explained`(잘 설명했어요) 또는 `together`
- "아니에요"만 하고 까닭이 없으면 `together`입니다. 맞장구·몰라요·되물음도 `together`입니다.

### 검사 (`validateFriendStep`)

**질문**
- 엘렌코스의 `checkQuestion`을 씁니다: 40자 이하, 한 문장, "요?"로 끝, 금지어 없음.
- 앞 질문과 같으면 안 됩니다(띄어쓰기 무시).
- **"~요, ~요?" 고르기 꼴이면 안 됩니다.**

**반응**
- 20자 이하, 물음표 없음.
- 칭찬·맞장구 말(맞아요·맞아,·맞네·맞죠·맞습니다·잘했·정답·훌륭)이나 금지어가 없어야 합니다. "총에 맞아서", "비를 맞아도"처럼 뒤에 서·도·야가 붙은 "맞아"는 칭찬이 아니라 통과합니다(`PRAISE`, 11-25).
- 반말이 아니어야 합니다(`isCasual`, 11-25). 쉼표·마침표·느낌표로 나눈 마디마다 끝이 "~구나·~네·~어·~다·~지" 같은 반말 꼴이면 걸립니다. "아", "오" 같은 한 글자와 "우와·아하·이야" 같은 감탄사, "~니다"는 통과합니다. 지난 점검 반응 6개에 대어 보니 "~구나" 3개만 걸렸습니다.

**끝**
- 한마디: 40자 이하, 비어 있지 않음, 금지어 없음, "학생이"처럼 3인칭이 아님.
- 다음 시간 질문: `checkQuestion` 통과, 고르기 꼴이 아님.

**고르기 꼴** (`isChoice`)
- "~까요, ~까요?"처럼 묻는 말 두 개를 막습니다. 앞의 "있잖아요,", "그런데요," 같은 이어 주는 말은 고르기로 보지 않습니다.
- "~일까, ~일까요?", "~일까요 ~일까요?"(쉼표 없음)도 막습니다.
- 실제 점검에서 나온 질문 72개는 하나도 걸리지 않았습니다.

**걸렸을 때**
- 까닭을 덧붙여 다시 받습니다(질문 2번, 끝 3번까지).
- 그래도 걸리면 기본 질문이나 기본 끝맺음을 쓰고, `fallbacks`를 1 올립니다.
- 표시는 따로 봅니다. 질문·반응·한마디만 걸리고 표시가 앞 질문과 맞았으면 그 표시를 씁니다. 맞는 표시가 한 번도 없었을 때만 `together`입니다. 맞게 답한 학생이 반응 한 줄 때문에 "함께 더 알아봐요"로 바뀌지 않게 하려는 것입니다(전체 검토에서 찾음).
- 기본 질문은 세 문장(뜻·까닭 / 더 말해 / 다시 말해)이 서로 다르고, 이미 한 질문은 다시 쓰지 않습니다. "몰라요"나 6자 이하 설명이면 "오늘 배운 것 하나만 알려 줄래요?"부터 씁니다.

### 맞장구친 오개념 (11-25 보완)

학생이 친구의 틀린 생각에 맞장구치면(mixup 뒤 표시 `together`), 같은 응답에 함께 온 다음 질문에 그 바른 생각이 섞이기 쉽습니다. 점검에서 두 번 연속 나왔습니다.
- `agreedMixup(turn)`이 참이면 그 응답의 질문(또는 끝맺음)은 버리고, 표시는 둔 채 `mark:"none"`으로 다시 받습니다.
- `buildMessage`는 지금까지 맞장구친 오개념마다 "[주의] 오개념 X(틀린 생각…)의 바른 생각(\"…\")은 질문·반응·한마디·다음 시간 확인할 것 어디에도 넣지 마세요"를 **그 뒤 모든 호출**에 붙입니다. 2번에서 맞장구치고 3번이 뜻 묻기였던 학생에게 마지막 한마디가 바른 생각을 알려 준 일이 있어서, 끝맺음까지 넣었습니다.
- 학생이 바로잡은 경우에는 호출이 늘지 않습니다. 맞장구친 학생만 1~2번 늘어납니다.

### AI 호출과 캐시

엘렌코스와 같은 구조입니다.
- system: `[프롬프트, 오늘 차시 원문(cache_control)]`
- user: `[단원 맥락(cache_control), 학생마다 바뀌는 글]`

학생 한 명에 호출 4~7번(맞장구친 학생이 많음), 하이쿠로 모두 7~17초가 걸렸습니다.

## 5. 실제 점검 (`tests/live-friend.html`)

- 앱에서 [설정]에 키를 넣은 같은 주소(예: `http://localhost:8765`)에서 엽니다. 키는 읽거나 출력하지 않고, 있는지만 봅니다.
- `?model=claude-haiku-5-5`처럼 주면 저장된 설정은 그대로 두고 이 페이지에서만 모델을 바꿉니다.
- 사례(`live-friend-cases.js`)의 칸
  - `explanation`: 첫 설명
  - `answers`: mixup이 아닌 질문에 차례로 넣을 답
  - `mixup`: mixup 질문의 기본 답
  - `byMisc`: 오개념 id별 답. 잘 아는 학생은 `CORRECT` 표(모든 오개념의 바로잡는 답)를 씁니다.
  - `expect`: `has`(나와야 할 표시), `at`(그 질문의 표시), `allTogether`, `firstKind`
- 결과 요약은 사용자님께 그대로 드리지 말고, 질문·한마디·다음 시간 질문을 **한 줄씩 읽어** "하면 안 되는 것"이 있는지 봅니다. 점수에 잡히지 않는 문제(정답 새기)가 여기서 나왔습니다.

## 6. 해 보며 배운 것 (다음 방법에도 해당)

1. **화면을 나누기 전에 기준 HTML부터 찍습니다.**
   - 리팩터 전 엘렌코스 화면을 `fixtures/`에 저장하고 장면마다 비교했습니다. "겉모습 그대로"를 눈이 아니라 비교로 확인할 수 있었습니다.
   - 장면을 찍을 차시도 중요합니다. 3-2를 고르면 범위에 오개념이 없어 장면이 달라집니다. 3-12로 고정했습니다.
2. **점수로는 정답 새기를 못 잡습니다.** 1회차는 17/18이었지만, 한마디·다음 시간 질문에서 정답을 알려 주는 말이 3건 나왔습니다. 결과를 줄마다 읽어야 합니다.
3. **잡을 수 있는 꼴은 코드 검사로 막습니다.** "~일까요, ~일까요?" 고르기 꼴은 프롬프트만으로는 다시 나올 수 있습니다. 정규식 검사로 막고 까닭을 돌려주게 했습니다.
4. **"안 됨" 예를 프롬프트에 그대로 넣으면 잘 듣습니다.** 한마디 정답 새기는 그 문장을 "안 됨"으로 넣자 다시 나오지 않았습니다.
5. **한 호출이 두 가지를 함께 정하면 코드가 끼어들 틈이 없습니다.** 표시와 다음 질문을 한 번에 받기 때문에, "방금 맞장구쳤으니 바른 생각을 넣지 말라"를 질문을 만들기 전에 알려 줄 수 없었습니다. 프롬프트 규칙만으로는 두 번 연속 새었습니다. 맞장구일 때만 다시 받는 것으로 풀었습니다(4장). 다음 방법을 설계할 때, 앞 결과에 따라 다음 출력이 달라져야 하는 곳은 처음부터 호출을 나눌지 정합니다.
6. **"주의"는 그 일이 있었던 바로 다음 호출만이 아니라 그 뒤 모든 호출에 넣습니다.** 다음 질문만 막았더니 마지막 한마디에서 샜습니다.
7. **메시지 내용 테스트는 학생마다 바뀌는 블록만 봅니다.** 첫 블록(단원 맥락)에 모든 오개념의 바른 생각이 들어 있어서, 전체 메시지를 검사하면 아무 메시지나 통과합니다(`noteText`).
8. **점검 사례의 답은 질문에 맞아야 합니다.** 차례로 넣는 답이 질문과 어긋나면 AI가 `together`로 보는 것이 맞는데, 점검에서는 "다름"으로 잡힙니다. 기대는 넉넉하게 쓰고(`firstKind: ["more","meaning"]`), 기록만 합니다.
9. **작업 환경 팁**
   - `core/ui.js`, `core/style.css`, `index.html`은 CRLF 줄끝입니다. Python으로 바꿀 때는 줄끝을 맞추고, 가능하면 Edit 도구를 씁니다.
   - Bash 히어독에 JS를 넣으면 "unexpected EOF"가 납니다. Edit·Write 도구를 씁니다.
   - `preview_start`가 8765를 이미 쓰고 있으면 다른 포트를 받아 빈 화면이 됩니다. 8765 서버가 있으면 그것을 씁니다.
   - 점검 스크립트 기다림은 한 번에 45초 안으로 나눕니다.

## 7. 남은 문제 (보완 후보 — 고칠지는 사용자님이 정하십니다)

**모르는 친구** (11-25에 사용자님이 고르신 보완 다섯 가지와 세 가지는 고쳤습니다. 다섯 가지: 맞장구 뒤 정답 새기, 설명 칸 Enter, 장난에 맞장구, 엉뚱한 화제, 기본 질문 겹침. 세 가지: 반응 존댓말, 칭찬 검사 좁히기, 도움말 칸 이름. 세 가지 뒤 하이쿠 6회차: 18/18, 대체 0, 정답 새기 0, 반응 48개 모두 존댓말)
1. **잘못 알아듣기가 학생이 말하지 않은 화제를 꺼냄(줄었지만 남음).** 5·6회차에도 헌병 경찰·임시 정부를 말한 학생에게 "나라 군대가 없어진 군인들은 그 뒤 무엇을 했어요?"가 나왔습니다(18명 중 2명). 이 질문은 잘못 알아듣기 꼴도 아닙니다. 6회차에는 쌀 이야기를 하지 않은 학생(#8)에게 쌀 오개념 질문이 다시 한 번 나왔습니다. 3번 질문을 늘 뜻·까닭 묻기로 하면 없어지지만, 잘못 알아듣기가 학생당 한 번으로 줄어듭니다.
2. ~~반응 말투가 "아, 그렇구나!"처럼 "~구나" 반말~~ → 11-25 고침. 프롬프트·형식 설명·검사 까닭의 예를 "아, 그렇군요!"로 바꾸고, 반말 반응은 `isCasual` 검사로 다시 받습니다. **새로 남은 것:** 반응 48개 중 31개가 "그렇군요"이고, 학생이 틀린 말에 맞장구친 뒤에도 "아, 그렇군요!"가 붙습니다. 칭찬은 아니지만 받아들이는 말처럼 들릴 수 있습니다. 맞장구(`together`) 뒤에는 "음, 헷갈려요." 쪽으로 쓰게 할 수 있습니다.
3. **다음 시간 질문이 학생이 말하지 않은 사실을 담기도 함.** 예: "일제는 왜 학교 선생님에게도 칼을 차게 했을까요?" 정답 새기는 아닙니다. 6회차에는 의병이 약해졌다는 말에 맞장구친 학생에게 "일제는 왜 의병을 누르려고 큰 부대를 보냈을까요?"가 나와, 바른 쪽을 조금 비췄습니다.
4. **소넷으로는 실제 점검을 돌리지 않았습니다.** 화면에서 한 번 해 본 것만 있습니다. `?model=claude-sonnet-5-5`로 돌려 볼 수 있습니다.
5. ~~반응 칭찬 검사가 "총에 맞아서"도 막음~~ → 11-25 고침. `PRAISE`는 뒤에 서·도·야가 붙지 않은 "맞아·맞네·맞죠·맞습니다·맞군요·맞구나"만 잡습니다.
6. **반응 칸이 문자열이 아니면 오류 화면이 됨.** 응답 형식이 문자열을 강제하므로 실제로는 거의 없습니다.
7. ~~선생님 도움말의 "살펴볼 생각" 칸에 친구의 질문이 들어감~~ → 11-25 고침. `friendHelp`가 묶음마다 `itemLabel: "살펴볼 질문"`을 붙이고, `helpLines`는 이것이 없으면 "살펴볼 생각"을 씁니다(엘렌코스 화면 비교 같음 10/10).
8. **반말 검사가 드물게 바른 말을 막을 수 있음.** 마디 끝이 "~네·~다·~라"인 이름씨(예: "우리 동네", "바다")로 끝나는 반응도 반말로 봅니다. 걸려도 까닭을 알려 주고 다시 받으며, 6회차에는 대체가 0번이었습니다.

**공통 틀 (사소한 것)**
- 시작 화면에서 방법을 바꾸면 화면 전체를 다시 그립니다. 고른 교과서·차시는 유지됩니다.
- 점검 페이지 두 개(`live.html`, `live-friend.html`)에 표 만들기 코드가 겹칩니다. 방법이 늘면 공통 도우미로 뺄 만합니다.
- 이번 점검 때문에 선생님 PC의 저장된 교과서·차시 선택이 천재·12차시로 바뀌었습니다(키·모델은 그대로).

## 8. 다음 방법을 만드는 세션에게

1. `docs/elenchus-handoff.md` → 이 문서 → 두 방법의 `*-views.js`를 읽습니다. 모르는 친구가 더 짧고 공통 부품만으로 짜여 있어 본보기로 좋습니다.
2. 흐름 파일(`methods/<이름>.js`)은 `friend.js`의 뼈대를 따릅니다.
   - `schemaFor` / `validate…`
   - `callChecked`: 까닭을 알려 주고 다시 받기 → 기본값 → `fallbacks`
   - 세대 번호로 `cancel`
   - `buildMessage`: 캐시 블록 두 개
3. 오답 탐정·반쪽 정답은 **문제를 데이터로 미리 만들고 검토**해야 합니다(`elenchus-handoff.md` 11장). AI가 그때그때 틀린 설명을 지어내게 하지 않는 편이 안전합니다.
4. 사용자님께는 설계 전에 한 번에 하나씩 묻습니다. 고르실 것은 2~4개 보기로 드립니다. 테스트 예시 5명분(낮은 수준, "몰라요" 포함)과 실제 점검 결과, 보완 후보 목록을 드리면 고칠지는 사용자님이 정하십니다.
